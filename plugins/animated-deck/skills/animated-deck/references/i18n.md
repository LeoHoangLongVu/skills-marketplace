# Translating a finished deck (comtor workflow)

A deck is one self-contained `.html`, so a translator (comtor) should not have to edit markup.
`scripts/i18n.py` externalises every translatable string into a flat JSON keyed by a stable
id; the comtor edits only values, and the script re-bakes the JSON into a **new single-file
deck**. The output stays one portable `.html` — the whole point of the skill is preserved.

## The three commands

```bash
# 1. tag translatable text with data-i18n="sNNN" and emit the source-language strings
python3 scripts/i18n.py key deck.html -o deck.keyed.html --strings strings.en.json

# 2. comtor copies strings.en.json -> strings.vi.json and translates the VALUES only
#    (keys stay; technical tokens already excluded — see below)

# 3. bake a strings file back into the keyed deck -> a new single-file deck
python3 scripts/i18n.py apply deck.keyed.html strings.vi.json -o deck.vi.html

# (re-dump current text from an already-keyed deck, e.g. after edits)
python3 scripts/i18n.py extract deck.keyed.html -o strings.en.json
```

`key` re-keys cleanly: it strips any pre-existing `data-i18n` first, then assigns ids
deterministically in document order (`s001`, `s002`, …). So it is safe to run on a deck that
was already keyed (it will not double-key), and the same deck always yields the same keys —
but if you add or reorder slides the ids shift, so regenerate `strings.json` from the current
deck version rather than reusing an old one. `strings.json` is in document order, so it reads
top-to-bottom like the deck.

## What gets translated, what is left alone

Keying is at the **plain-text-run** level, so a translator never sees or edits markup. A
pure-text element is keyed on itself; an element that mixes text with inline tags has each text
run keyed in its own wrapper, leaving the tags and numbering alone. So a line like
`<li><span class="n">01</span>Overview — what it is and why<span class="s">slides 3–4</span></li>`
becomes **three** independent fields the comtor can edit safely — `Overview — what it is and
why` and `slides 3–4` are translatable, the `01` is left as numbering — and none of them
exposes a `<span>`. (Trade-off: a sentence with inline `<code>`/`<b>` splits into a run on each
side of the tag; that is the price of never letting a translator break the markup.)

- **Translated:** visible prose in headings, `p`, `li`, `td`/`th`, captions, leaf `<div>`s and
  inline `<span>`/`<b>` runs, plus **SVG `<text>`** (diagram node labels and edge captions).
- **Left alone (never offered for translation):** anything inside `<pre>`/`<code>`/`<script>`/
  `<style>`, and any run whose text is a lone technical token — a path, filename, or identifier
  carrying `/ . _ : \` (so `deck.pptx`, `/animated-deck`, `.html`, `flow.md`, `pptx_theme.py`
  are skipped), and pure numbers (`01`, `1280×720`). A plain word like `Content` or `Template`
  is real prose and **is** translated. This matches the language rule: translate prose, keep
  technical tokens verbatim.

## GUI for a non-technical comtor (no terminal, no AI)

For a translator who should not touch a terminal, open **`scripts/i18n-editor.html`** in a
browser. It is a self-contained offline tool (no server, no network, no LLM):

1. **Open deck** — pick the deck `.html`. It auto-keys in memory using the same rules as the
   CLI (prose + SVG labels in, code/paths out), so it works on a deck that was never keyed.
2. Every string shows as a row: key, source text, and an editable field. Filter with the
   search box. Optionally **Load strings.json** to pre-fill an in-progress translation.
3. **Apply & download deck** — bakes the edits in and downloads a rebuilt single-file deck;
   the live preview updates so the comtor sees the result. **Save strings.json** exports the
   translation table for reuse / version control.

It re-implements the same contract in the browser (DOM-based, deterministic) — identical
string set to `i18n.py` (verified). Use the CLI for scripted/batch runs, the GUI for a human
translator.

## Authoring for translation

Retrofitting works (`key` assigns ids by document position), and is the normal path. If you
know up front a deck will be translated, you can also hand-author `data-i18n="key"` on text
nodes with meaningful keys (`cover.title`, `s.intro.lede`) — `extract`/`apply` honour them and
the strings file becomes self-describing. Either way the contract is the same.

## After applying — verify

The one thing this cannot prevent is a translation that is **longer than the source** and
overflows a slide (German and Vietnamese both run long). Always re-render:

```bash
scripts/shot.sh deck.vi.html 1 <n>          # look at every slide
node scripts/check_diagram.js deck.vi.html  # a label that grew may break a diagram
```

If a string overflows, shorten the translation or split the slide — do not shrink the font
below the 14px floor.
